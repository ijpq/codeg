# 0.41.1-fix1 — conversation readiness and complete rule handoff

This Windows Server/Setup candidate rebases the private fork onto upstream
v0.41.1 (`8a7565edf3c1d19ef3e9aa61ab20f8b55713dada`). It retains the previously
released business conversation, Pi, external submission, task timing, delivery,
Office review, native Plan/Goal and virtualized scroll fixes.

Both application forms share the following changes:

- Codex and Pi restore through the stable business conversation ID. The backend
  verifies the native session and returns a readiness receipt, including the
  explicitly supported provisional first-prompt state. An absent replay event
  no longer leaves an otherwise verified connection unusable.
- Attach handlers are scoped to their subscription generation and connection.
  Delayed callbacks from an old connection cannot clear readiness or remove its
  replacement. Recovery retains the original queued client message ID; backend
  idempotency remains responsible for rejecting duplicate execution.
- Restore failures remain visible even when an older connection still exists.
  The composer ends its waiting state and offers the existing retry flow.
- Applicable instance/workspace rule files are transferred completely, with
  source attribution and a versioned digest. Old truncated rule snapshots are
  rebuilt, including for sessions whose history handoff cursor already advanced.
  A delivery receipt advances only after prompt acceptance; unchanged rules do
  not accumulate repeatedly in subsequent prompts. Native-session replacement
  invalidates its receipt. Admission is not execution confirmation: after a
  failed or cancelled ordinary round, the next ordinary prompt includes complete
  rules again. Updated rules must reach the engine before a Goal
  can bypass ordinary prompt delivery.
- An unreadable, invalid UTF-8 or oversized required rule source produces an
  actionable error instead of silently delivering a prefix. The complete-file
  limit is 128 KiB and the combined rule-context limit is 192 KiB. Skill catalog
  descriptions remain discovery metadata; they do not claim full Skill loading.
- Catalog validation recognizes the private native Codex CLI and runs it
  directly, rather than resolving a missing `@openai/codex/bin/codex.js`.
  Explicit user runtime paths and separate instance profiles remain intact.

The additive `delivered_rule_digest` database migration retains all native
session bindings and business history; its down step preserves this metadata.
As with previous releases, application rollback uses the whole pre-upgrade
offline data snapshot with the matching runtime group, rather than opening the
upgraded database in an older application's migration runner.

The paired Pi runtime remains `pi-acp 0.0.34-codeg.2`, commit
`0d0fbe08a0a7eaacbb1061aea79c5fcb6a1e26c5`, Pi 1.4.0 and Node 24.16.0.
Codex remains the private 0.162.1-codeg.1 CLI and 2.2.2 ACP. No new Pi protocol
change is needed for this application binding/rule-delivery correction.

Acceptance distinguishes actual packaged CLI/ACP and browser execution against a
deterministic local model endpoint from authenticated live-model behavior. The
latter is not confirmed in this development environment: no isolated Codex/Pi
model credentials were present. Request-content checks independently verify long
rule tails and rule revisions; they are not evidence that a live model performed
“小弟” delegation or followed document-only presentation rules. Service-tier
requests likewise do not establish that an upstream relay provided acceleration.

Release acceptance must include fresh/upgrade/rollback installation, resources,
migrations and dependency inventories; native agent restore/handoff and repeated
composer sends in both forms; multi-client Server state, Office review and scroll
regressions; public re-download and SHA256 checks. No current user instance is
updated by publication.
