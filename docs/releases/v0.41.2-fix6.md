# CodeG 0.41.2-fix6

修复 Pi 原生压缩与任务终态脱节。Pi 1.4.0 的 `prompt` 受理确认在预处理压缩之后
返回；旧适配器的普通 30 秒确认期限会先结束 ACP 请求，且未停止仍在工作的 Pi。
旧适配器另只监听 `auto_compaction_start/end`，漏掉当前 `compaction_start/end`。

新适配器在期限到达时查询原生状态：确仍压缩则保持同一请求，不重发 prompt；
普通受理无回应、健康检查失败、进程退出等仍有界报错，先确认原生 idle 或所属子进程
退出再释放任务，并保留原始原因。取消清理原生队列并等待实际停止。`/compact`
也通过同一任务队列及取消流程；成功重试不再被此前临时错误污染。

共用前端以一张压缩记录显示开始、真实整理阶段和已耗时，以及完成、失败或取消。
上游没有百分比，不显示虚假进度。成功事件与经过内容核对的原生条目 ID 关联，
避免实时记录和历史重复；历史摘要直接来自原生记录，不篡改 JSONL。
历史没有记录的触发方式、前后 token 或耗时保持缺失，不推测填充。

Windows Server 与 Setup 使用同一核心和前端。配套运行组：Pi ACP
`0.0.34-codeg.4`（`d5e7fd87ef4c277e3db46986adc21789076659f2`）、Pi `1.4.0`、
Node `24.16.0`，保留原上游许可证。Codex 运行组、原生 Plan/Goal、虚拟列表与追底、
业务交接/恢复、多 Provider、外部投递、产物和 Office 功能保留，并继续执行原门禁。
不改变用户模型、中转、认证、规则、Skill、历史、工作区和生产实例。

本次新增最终包输入框验收：真实 Pi 处理长历史并压缩超过 30 秒，然后只回复一次，
接着发送；压缩中离开/返回/刷新、多客户端附着、失败与重试、停止、进程重启后续发。
这些用例使用隔离的确定性模型 HTTP 服务延迟原生摘要请求，不是假造压缩事件，
也不宣称验证了用户认证中转的实际推理、费用或延迟。

本文件描述实现与验收范围，最终成功状态以本版本 Release 的双包验证报告为准。
