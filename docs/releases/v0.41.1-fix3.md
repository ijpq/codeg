# 0.41.1-fix3 — verified restore through real composer execution

This release includes the business identity, readiness, active-turn receipt and
complete versioned rule delivery fixes described in [fix2](v0.41.1-fix2.md) and
[fix1](v0.41.1-fix1.md). Neither candidate passed its complete downloaded-package
acceptance, so both tags remain unpublished and their evidence is retained.

The fix2 Windows builds succeeded. Installed Setup passed actual composer
acceptance, but Server Web failed its first newly created Codex round: the
expected no-external-session rejection was a structured command error. A local
`String(error)` turned it into `[object Object]`, preventing the controlled
session/new fallback. Both connection-provider and lifecycle errors now use the
existing shared structured-error decoder. Saved historical sessions cannot
enter that fallback. Six Codex/Pi regressions for message/detail errors and
historical-session preservation failed before this change and pass afterward.
This additional fault is not evidence that the user's old Pi incident had only
this cause.

Earlier acceptance prepared some connections with backend API calls and treated
successful restore, first reply and history checks as sufficient. This bypassed
the composer's readiness, business binding and durable send queue. It missed a
first-turn active attachment and the Server-specific structured rejection. The
release now requires real composer sends for five consecutive Codex/Pi rounds,
failed restore/retry, navigation, refresh, connection loss and process restart.
Both draft and published packages are downloaded and tested independently.

An additional fixture uses the actual v0.40.0-fix6 packages to create a business
conversation, complete a Codex round, switch to Pi and complete another round.
The candidate upgrades that isolated data and retains both native bindings and
the old history. Its installed Pi launcher is held until a real composer input
has entered the durable restore queue for five seconds, then delegates to the
unchanged installed ACP and Node. The same input must receive an actual native
reply once. Later composer rounds cover another reply, tab switches, reload,
connection loss, Pi→Codex→Pi and process restart.
Each synthetic input also has a unique marker observed independently in the
selected engine's real provider request, once, and absent from the other engine.
In-place tab navigation does not reload the application; queue removal after
completion is asserted separately from the reply and native readiness.
Read-only page diagnostics expose the actual computed send gate and its
business/session/Agent/workspace identity, prompt readiness and transport state.
Acceptance records these fields and queue IDs/states before input, during the
five-second wait and after every completed reply, including restart. It neither
logs queued text nor infers the user's live page state from its on-disk bundle.
The fix6 Pi source used a session-only restore without business identity; the
reported ready-without-binding logs are consistent with that path. The user's
specific live blocking field and local queue have not been sampled here.
The existing fix4 upgrade and offline snapshot/group rollback checks remain
mandatory. Test children use only
disposable data, profile and installation paths; no running user instance or
external automation is modified.

The adapter group remains Pi ACP `0.0.34-codeg.2`, commit
`0d0fbe08a0a7eaacbb1061aea79c5fcb6a1e26c5`, Pi `1.4.0` and Node `24.16.0`;
Codex is `0.162.1-codeg.1` with ACP `2.2.2`. These application-level fixes do not
require a new Pi adapter build. Both Windows packages include this group, the
matching CodeG MCP, static frontend and additive migrations. Existing explicit
runtime paths, authentication and user histories remain independent. Rollback
uses the pre-upgrade offline data snapshot and matching complete runtime group.

Native CLI/ACP/MCP tests use deterministic local model endpoints and verify
actual requests and replies. They do not prove authenticated live-model
compliance with “小弟” delegation or document presentation rules. Those behaviors
remain unverified without an isolated model configuration; complete rule-tail
receipt is tested separately. Relay priority speed, applied tier and pricing
remain unverified unless returned by that relay. Pi does not advertise native
Codex Plan/Goal, and private engine compression state is not shared losslessly.
